6.0 FUNCTIONAL REQUIREMENTS

6.1 General

FR-6.1.1V2 shall be built on its own branch in app2/, leaving V1 usable until cut-over (D-1).
FR-6.1.2V2 shall be plain JavaScript modules served without a build step (A-2).
FR-6.1.3Every source file shall begin with a header comment stating what it does; the Notes popup shall show it.
FR-6.1.4An automatic check shall verify the call rules of Section 5.4 (which module may import which) and fail the build on a violation. It shall run with the other checks.
FR-6.1.5Only main.js shall read or write the browser's window object.

6.2 Kernel: paths

A path is an ordered array of points with a flag saying whether it closes on itself. Figure 5 shows an open path and a closed path. When a path is closed, an index past the last point wraps to the first.

[[FIG path_figure | Paths: the array of points underneath every drawing]]

Kernel operations fall into four families. Makers build a path from a rule. Figure 6 shows that a line, a circle and a parametric curve differ only in their rule: each is sampled into a path the same way, which is what removes the parametric and non-parametric divide (P-18).

[[FIG makers_figure | Makers: three rules, one kind of result]]

Shapers turn a path into another path. They are V1's createNodes pipeline (sample finely, space by arc length, bias, jitter) taken apart so that each step works on any path, not only an ellipse. Figure 7 shows the principal shapers.

[[FIG shapers_figure | Shapers: path in, path out]]

Connectors join the points of one or more paths into stitch lines. Each of V1's string-art objects is one connector applied to one or two paths, as Figure 8 shows.

[[FIG connectors_figure | Connectors: four rules that produce four familiar objects]]
FR-6.2.1The kernel shall represent a path as { points, closed } (Section 8).
FR-6.2.2The kernel shall provide makers at least for: line, polygon, circle, ellipse, arc, spiral, and parametric curve p(t) over a range of t.
FR-6.2.3The kernel shall provide shapers at least for: move, rotate, scale; even spacing by arc length; spacing bias; jitter; trim; reverse; start at index; every k-th point; split; join; mirror.
FR-6.2.4Jitter shall take a seed, so the same settings give the same picture on every redraw.
FR-6.2.5The kernel shall provide connectors at least for: pairwise between two paths, skip by s, multiply by k, all pairs, ring, and connection among several paths (Linked Circles).
FR-6.2.5a [B]Connectors shall be one pluggable family (I-21), each a file declaring its settings, added without other edits. The family shall include at least: point i to i; offset (i to i + k, stopping or wrapping); reversed; every nth; part of an arm (from, to); growing skip (i to i + s0 + i·g); times table with negative and fractional factors; all pairs; mirror; and the corner stitch (arm a→c to arm c→b), which is the most used rule in the owner's ideabook. Every setting shall have a default, and a connector shall draw whatever its settings produce, however odd (D-15), stopping only where the result would be undefined.
FR-6.2.5b [B]The kernel shall provide composite makers proven by the Ideabook hints: star of corners (n tips, an inner radius, a twist), polygon corner stitch (from edge mid-points or whole edges), segment stitch, zigzag row, growing chords and offset rings, so that the common string-art constructions are one call each.
FR-6.2.6When two paths of different length are connected, the connector shall either resample to match, or stop with a message naming both lengths and the missing index, as the owner asked in October.
FR-6.2.7The kernel shall provide finders at least for: ends, midpoints, extremes, lobe tips, cusps and crossings. A finder shall name a point by feature (for example "tip of lobe 3"), not by array index.
FR-6.2.7a [B]Crossings of curves shall be called intersections and treated as nail candidates, shown with their own mark, distinct from the magic points (ends, middles, tips, cusps). See 6.21.
FR-6.2.8A curve shall have two samplings: a fine one for display and an n-point one for nails and stitches.
FR-6.2.9No kernel function shall read or write anything other than its arguments and its return value.

6.3 Generators

A generator is one file that describes one drawable object or one script. It replaces both the V1 registry object and the V1 scriptInfo script. Listing 1 shows a complete generator for the Parabola. Its corner is two handles, independent until welded (A-5).

 1 /* generators/parabola.js  -- two arms stitched pairwise: the curve-stitch parabola. */
 2 export const meta = {
 3   id: "parabola", version: 1, title: "Parabola",
 4   tags: ["stitch"], notes: "Two arms stitched at equal steps."
 5 };
 6
 7 export const params = {                 // one entry per setting; controls come from this
 8   a:      { type: "point", handle: true, default: [100, 100] },
 9   b1:     { type: "point", handle: true, default: [100, 300] },   // arm 1 corner end
10   b2:     { type: "point", handle: true, default: [100, 300] },   // arm 2 corner end
11   c:      { type: "point", handle: true, default: [300, 300] },
12   steps:  { type: "int",   default: 18, min: 3, max: 64, label: "Steps" },
13   trim:   { type: "int",   default: 0,  min: 0, max: 15, label: "Trim" },
14   color:  { type: "color", default: "#0044cc" }
15 };
16
17 export function build(p, k) {           // k is the kernel, passed in
18   const arm1 = k.trim(k.line(p.a,  p.b1, p.steps), p.trim, 0);
19   const arm2 = k.line(p.b2, p.c,  p.steps);
20   return { paths: { arm1, arm2 },        // infrastructure: where discs may go
21            stitches: k.pairwise(arm1, arm2),
22            style: { color: p.color } };
23 }
Listing 1. A complete generator. There is no init, update or draw, and nothing is stored on the object.
FR-6.3.1A generator file shall export meta, params and one of build(p, k) (geometry) or run(api) (a painting script). It may export drag(name, position, p) and migrate(oldVersion, p).
FR-6.3.2meta.id shall be permanent: it is what saved documents refer to. Renaming the file shall have no effect on documents. Two files with the same id shall both be reported and neither loaded.
FR-6.3.3meta.version shall be a whole number. When it rises, migrate shall convert settings saved under earlier versions.
FR-6.3.4build shall return, in one result, everything needed by every reader: paths (infrastructure), stitches, named points, bounds and style. There shall be no second method that must agree with it.
FR-6.3.5A setting marked handle: true shall be draggable on the canvas. Dragging writes that setting through a command and build runs again.
FR-6.3.6Where a handle's behaviour is not "move this point", the generator's drag shall return the new settings (for example the Circular Parabola Multi handle that separates and joins copies).
FR-6.3.7A generator may declare a handle that moves others (for example a midpoint that moves a whole arm) with moves: [ ... ].
FR-6.3.8Each generator file shall be checked against the format when loaded. A failure shall show a badge with the reason on that item only; the rest of the library shall load.
FR-6.3.9The 14 V1 Draw objects shall be rewritten as generators (D-5). Exact reproduction of V1 output is not required (D-4). Before each is written, a one-page feature list (controls, handles and what each does, infrastructure, special behaviour) shall be drafted from V1 and corrected by the owner, so nothing distinctive is lost.

6.4 Settings schema and controls

FR-6.4.1Each setting shall be declared once, with its type, default and limits, in params. There shall be no separate controls block (P-14).
FR-6.4.2The types shall be: int, number, angle, color, choice, bool, text, point, points (a list) and pathRef (a reference to another layer's path).
FR-6.4.3Each type shall have a default widget. A setting may name a different widget with widget:. Conversion and checking of values shall happen in one place, by type, not in each widget.
FR-6.4.4A widget shall not write a setting. It shall send one SetParam command. A whole slider movement shall be one undo step.
FR-6.4.5A setting may carry section: (grouping, shown as an accordion) and showIf: { setting: value } (conditional display).
FR-6.4.6Number settings shall show a number box beside the slider for exact entry, and every setting shall offer reset to its default.
FR-6.4.7Buttons are actions, not settings, and belong to the commands table (6.9). Static text belongs to notes or help.
FR-6.4.9 [B]A common settings set (colour, line width, steps, rotate, scale) shall be shared by every generator and shown in one standard panel; each generator declares only its own settings beyond it (I-4). Standard groupings of settings may be shown as tabs.
FR-6.4.8A converter shall turn V1 declarations into the schema mechanically: range with whole-number bounds and step 1 to int, other range to number (or angle where named so), color and colorPicker to color, select and radio to choice, checkbox to bool, any leftover pointPicker to a handle.

6.5 Documents, the point table and welds

A document holds layers and a point table. A layer's handles name point numbers; they do not hold coordinates. A table entry either holds a position (a free point) or refers to a place on another layer's path (an attached point). These two kinds of entry give exactly two kinds of weld.

Shared point. Two handles name the same free point. Figure 9 shows two Parabola layers sharing point 11. The point is stored once; dragging it moves both layers. This is the owner's rule D-3: the table entry is the point, so nothing is copied and nothing can drift (P-6).

[[FIG weld_shared | A shared point: two layers name point 11]]

Attachment. A handle names a point that lies on another layer's path, at a fraction t along it or on a named feature. It is one-way: the path decides where the point is and the handle follows. Dragging the attached handle slides it along the path. Figure 10 shows a line attached to a circle. Anchored discs, handles dropped mid-arm and scaffold all work this way.

[[FIG weld_attach | An attachment: point 14 lies on layer L3's path]]

Because attachments are one-way, layers can be evaluated in order: each after every layer it is attached to. A loop of attachments cannot be evaluated and is refused at the moment the weld is made, with a message (Figure 11). The V1 propagation walk, its snapshots and deltas, its four special cases and cornerPartners() are not needed.

[[FIG eval_order | Evaluation order, and a loop refused at weld time]]
FR-6.5.1A document shall hold a point table; each entry shall be either a free point {x, y, z} or an attached point {on, t} or {on, feature}. [B] z is carried from the first checkpoint, default 0 (D-11); flat work never sees it.
FR-6.5.2Point numbers shall be permanent and never reused (V1's nextPoint rule). Disc numbers, point numbers and nail numbers shall be the same numbers.
FR-6.5.3Welding two handles shall make them name one free point. Unwelding shall copy the point under a new number and point one handle at the copy.
FR-6.5.4Dropping a handle within the snap radius of another handle shall weld them on release, never while passing over (V1 Phase 8 next pass behaviour kept).
FR-6.5.5Attaching shall be refused, with a message naming the layers, if it would create a loop.
FR-6.5.6A document shall carry format (a whole number). The loader shall apply one upgrade step per format number, so old files always open. Unknown generator ids shall open as visible placeholders with their data kept.
FR-6.5.7A document shall contain no derived values and no code. Anything computable shall be computed on load.
FR-6.5.8A document shall record the units and scale chosen for output (O-1). Documents imported without a scale shall show "scale not established".
FR-6.5.9When a path's point count changes, an attachment by node shall move to the nearest node; one that cannot be placed shall be reported, never silently moved to whatever point now has its old index.
FR-6.5.10A layer may be a reference to another saved document (nesting). A reference shall follow edits to that document; a copy shall not. Break apart shall expand a nested document or turn a generator's stitches into layers.
FR-6.5.11A layer shall have a role: stitch, guide, scaffold or image. Guides and scaffold shall never print. Scaffold is one-way by construction: other layers attach to it.

6.6 Commands and undo

Every change to a document goes through a named command. Before a command runs, the whole document is copied onto the history (A-3). Undo restores the previous copy; redo moves forward. A snapshot cannot be wrong in the way a hand-written reverse function can: it puts back exactly what was there, partners included.

[[FIG undo_stack | Snapshot history, the current position and the saved position]]
FR-6.6.1Nothing shall change a document except a command. Commands shall at least cover: insert layer, delete layer, set setting, move point, weld, unweld, attach, add disc, delete disc, move or turn layer, reorder layers, set layer colour, set output inclusion, break apart, revert to saved.
FR-6.6.2One gesture shall be one undo step: a handle drag is recorded on release; a slider when movement starts, the whole movement one step; consecutive arrow-key nudges one step until a pause or a change of selection.
FR-6.6.3Undo shall not cover session changes (selection, mode, Show All, zoom) or file operations (Save, Save As, Archive). File operations shall continue to ask first where V1 asks.
FR-6.6.4"Unsaved changes" shall mean the history position differs from the position at the last save. Undoing back to that position shall make the document clean.
FR-6.6.5History shall last while the document is open, including across tab switches, and shall not be saved in the file.
FR-6.6.6Ctrl+Z shall undo and Ctrl+Y shall redo, except while a text or number field has focus, where the field's own undo applies.
FR-6.6.7Delete Layer shall no longer warn that it cannot be undone. Reset shall become "revert to saved", an ordinary command that can itself be undone.
FR-6.6.8Every command shall end by calling one refresh(), which redraws the open tab's regions in a fixed order (A-4).

FR-6.7.1Document, session and interaction state shall be held in separate objects. Only the document shall be saved or undone.
FR-6.7.2The active layer shall be session state. Choosing a layer shall not mark the document changed.
FR-6.7.3Choosing a layer and reordering layers shall be separate actions. V1's bring-to-front on select may remain as an option (O-6).
FR-6.7.4"Hidden while editing" shall be session state; "left out of output" shall be document state. Show All shall reveal hidden layers as in V1.
FR-6.7.5Switching tabs shall close the old tab (detach its listeners, clear its regions) and open the new one, which draws from its own state. There shall be no needsUpdate or saved flags.
FR-6.7.6A tab shall re-read the catalog when it opens.

6.8 Catalog and storage

FR-6.8.1A folder shall be a category. patterns/builds/myStar.js is in Patterns, category builds. There shall be no registration step and no hand-maintained list.
FR-6.8.2An item's title, tags and notes shall come from its file (meta, or the header comment for legacy scripts). Its status shall be kept in a small metadata file beside it. Figures carry their title inside the document.
FR-6.8.3The catalog index shall be built from the folders, never stored as the authority. If curation needs order or hidden entries, these shall be fields in the metadata file (O-5).
FR-6.8.4Thumbnails shall be a cache: made when missing or out of date, deletable at any time.
FR-6.8.5Storage shall be the only module that reads files or calls the Node service. It shall offer named operations (open, list, save, save as, archive, write thumbnail, open in editor), never paths or request names to its callers.
FR-6.8.6Saving shall be atomic for the document file. A thumbnail or index failure shall not turn a successful save into "not saved"; the index shall be repairable from the folders.
FR-6.8.7One name check shall apply everywhere, rejecting Windows reserved names (CON, PRN, AUX, NUL, COM1 to COM9, LPT1 to LPT9), trailing dots and spaces, and names differing only by letter case from an existing name.
FR-6.8.8V1's path-safety rules (safePaths.mjs) and foreign-origin refusal shall be kept.

6.9 Adding scripts and objects while the application runs

This is a defining feature (D-6). Saving a file into a library folder is the whole procedure. [[REF dynamic_add]] shows the sequence.

[[FIG dynamic_add | Adding a script: save the file, and it appears]]
FR-6.9.1The Node service shall watch the library folders. On a file added, changed or removed, it shall read the item's description without running it, update the index, and notify the open application over a connection kept open for the purpose.
FR-6.9.2A new item shall appear in its list within two seconds of the file being saved, with no restart and no Rebuild.
FR-6.9.3When an open item's file changes, it shall rerun with the current settings kept.
FR-6.9.4Code shall be loaded with the file's change time in its address, so an edited file is never served from the browser cache.
FR-6.9.5At start-up the service shall scan the folders once, so files added while it was stopped are found. This scan replaces the V1 manifest check.
FR-6.9.6A generator saved into generators/ shall appear in the Figures Insert list as a full object, with no other code changed.
FR-6.9.7"New script" shall write a skeleton native script into a chosen category and open it in VS Code. "Import" shall accept pasted code or a chosen file.
FR-6.9.8Outside libraries a script needs shall be kept in vendor/ so everything works without the internet.
FR-6.9.9 [B]Plugins (I-1): makers, shapers, connectors, finders, generators, templates and output engines shall all be found the same way, by saving a file in their folder, each declaring kind, name, version and its settings. This is settled before CP-0 because it decides how the kernel is loaded.

6.10 Script host and the ingestion ladder

FR-6.10.1Every script shall run in an isolated frame with a fresh canvas and fresh state. Nothing shall carry from one run to the next (P-12). Animation frames, timers and listeners shall be stopped when the item closes.
FR-6.10.2An error shall show as a badge on the item with its message; a run exceeding a time limit shall be stopped. The list shall keep working.
FR-6.10.3Three kinds of script shall be accepted: native (FR-6.3.1), legacy (V1 runPattern and scriptInfo, run through an adapter that supplies the old names inside the frame), and foreign (any canvas code, run through the recorder).
FR-6.10.4The recorder shall supply an object with the canvas drawing methods that records each line and arc as data instead of drawing. A recorded script's output shall be placeable in a figure as a frozen layer.
FR-6.10.5On first sight of a script, the host shall run it once and save beside it: a report (what it drew, likely stitches, number literals that look like settings, globals touched, internet use, animation, run time) and a thumbnail. Its status shall be new.

Adapting a script to built-in controls proceeds by levels ([[REF ladder]]). Each level is proposed by the importer, reviewed by the owner, and approved separately; the script works after every level. Level 3, with the owner's minimizing, is promotion: the owner's rule that playpen scripts are never promoted as-is is kept.

[[FIG ladder | The ingestion ladder]]
FR-6.10.6Level 1: the importer shall read the script's structure with a JavaScript parser and propose a typed settings entry for each independent top-level number literal and loop bound, with name, type and range. It shall not propose derived values (x2 = x1 + xLength) or constants (Math.PI / 2).
FR-6.10.7Level 2: the importer shall propose point settings with handles from paired names (x1/y1, cx/cy) and points built from literals.
FR-6.10.8Level 3: the importer shall draft a recipe from the recorder's stitch detection (for example "pairwise between two lines, 18 steps").
FR-6.10.9Each level shall be shown in a review panel: the proposed settings (tick, rename, change ranges), a live preview of the controls, and the code change. Accepting shall rewrite the file and keep the original beside it. Nothing shall be rewritten without approval.
FR-6.10.10The first test of the importer shall be patterns/builds/OverlappingStars.js; its Level 1 proposal shall be compared with the hand adaptation in V1's OVERLAP.js.

6.11 Rendering and physical output

FR-6.11.1Renderers shall be the only code that paints. Each shall take geometry and view options and return pixels or a file.
FR-6.11.2Final (points only) shall be a renderer option, not a flag read by objects.
FR-6.11.3The canvas renderer shall draw, in order: layers (with dimming), discs, weld marks, then the interaction layer (handles, selection) on its own canvas.
FR-6.11.4Output engines shall at least include: SVG; a true-scale PDF with a scale bar and a 100 mm calibration line; and a nail list (number, x and y in the chosen units, weld group).
FR-6.11.5A weld group (a shared point) shall print as one nail. Coincident points that are not welded shall follow a stated grouping rule shown in an output preview (O-2).
FR-6.11.6A spacing check shall take nail diameter and clearance (O-3), and highlight and list pairs that are too close. It shall not prevent an experimental drawing from being made.
FR-6.11.7Tiling across several sheets, with overlap and alignment marks, should be provided if the owner's boards exceed one sheet (O-7).
FR-6.11.8Thumbnails shall be the renderer drawing small onto its own canvas, never the main canvas.
FR-6.11.9 [B]Each printed nail shall keep where it came from (layer, arm, step). The nail template may then colour each nail by its step along its arm, in a repeating cycle of five colours, so the builder, going up by a constant, does not lose his place (I-14). The cycle is off by default; the owner has a colour laser.
FR-6.11.10 [B]Output engines shall be able to write one file per layer (SVG or DXF for laser-cut layers mounted at depth) and, later, a 3D format for curves extruded in space (I-11). Mounted layers need little more than V1's roles and per-layer print.

6.12 Help, notes, menus and the screens

FR-6.12.1Help pages shall be Markdown files, edited in VS Code. TinyMCE shall be removed.
FR-6.12.2Every menu item and button shall be an entry in one commands table: { id, label, enabledWhen(state), run() }. A disabled item shall say why. [B] Each entry also carries its scope; see 6.13.
FR-6.12.3"Panel" shall mean a page side area and "canvas layer" a drawing surface. "Overlay" shall not be used.
FR-6.12.4Home, Draw, Patterns, Figures, Gallery and Utilities shall keep their V1 purposes (A-1). Draw shall be a one-layer document; a saved Draw setting shall be a saved document.
FR-6.12.5Save As shall use one form showing category, title and destination, replacing V1's chain of prompts.
